## 1. 概述

本版把 v0.8.0 之后发现的 12 个问题放在一起修：**用户用一句话给信息，Skill 自动查完能查的，直接在对话里出一张能决定“下一步做什么”的分数卡**。分三批做，P0 修错误和脏话术，P1 改卡片和入口，P2 补新检查；P0 单独做完也可以先发布为 v0.8.1。

2026-11-04 负责人用 v0.8.0 跑了一张真实卡（客户名称已隐去，风险 0/100），暴露出的现象就是本版的依据。最终需求：一句话进、尽可能多维度查、分数卡美观清晰且有决策价值、功能完善、简单易用。

| P2 | 注册库自动查、招标专项 | P-11、P-12 | 时间不够就推迟 |

## 4. P0 修复（可单独发布为 v0.8.1）

P0 只修错误和显示，不改评分审核逻辑，全部现有测试不改就必须通过（除 4.4 里列出的格式断言）。

### 4.1 P-01 仿冒域名误报

原因：`compare()` 里只要域名核心标签以品牌名开头或结尾就返回 `affixed`，分数 0.80。品牌名很短或是普通单词时（ups、bp、dhl、apple、intel），`groups`、`pineapple`、`intelligent` 都会命中。

修法（Python 与 Node 同步）：

```python
SHORT = 5  # 品牌核心标签长度 <= 5 视为短品牌
if target_label.startswith(brand_label) or target_label.endswith(brand_label):
    remainder = target_label.replace(brand_label, "", 1).strip("-")
    if "-" in target_label:                      # 品牌名是连字符分隔的独立词段
        return "hyphenated", 0.80                 # 沿用原行为
    if len(brand_label) <= SHORT:
        if remainder in RISK_WORDS:               # upsexpress、applesupport 等
            return "affixed", 0.80
        # 其余短品牌嵌在普通词里（groups、pineapple）不算仿冒
    else:
        return "affixed", 0.80                    # 长品牌（maersk）行为不变
```

`RISK_WORDS` 写在 `scripts/brands.json` 的新字段 `risk_words`（不写进代码），初始值：express、track、tracking、pay、payment、invoice、login、secure、support、service、services、shipping、cargo、freight、logistics、customs、delivery、parcel、mail、bank、verify、account、official。“group”“supply”“lines” 这类普通公司词不进列表。

行为变化要写进 CHANGELOG：`dhlgroup.com`、`fedexgroup.com`、`dhlsupply.com` 不再被“仿冒”单独触发，靠域名过新（RF-DOM-002）等其他红旗兑底。

回归用例写进 `tests/cases/` 目录下新增用例文件 A23、A24（仓库里可以新增用例文件，精简包由构建脚本合并，不占文件数），两组都要覆盖：

| 应不判仿冒（误报回归） | 应判仿冒（真阳性） |
| --- | --- |
| harborrimgroups.example、sunsetgroups.com、cups.com | ups-track.com、upsexpress.com |
| pineapple.com、intelligentsolutions.com、bpharma.com | dhl-express-pay.com、fedex-login.com |
| mastersteel.com、cupsupply.com | app1e.com（homoglyph）、apple-support.com |
| （新行为记录）dhlgroup.com、fedexgroup.com | maersklines.com、mymaersk.com（长品牌不变） |

### 4.2 P-02 制裁名单自动下载

- `sanctions_check` 发现没有缓存或缓存超过 7 天，就自动调用 `update_sanctions` 下载 OFAC SDN 官方 CSV，并写入 `.cache/sanctions/`（已被 .gitignore 忽略）。
- 加 `--no-update` 参数关闭下载；测试和离线模式一律用它。下载失败返回 `status: "unavailable"` 和原因（`download-failed` 或 `no-network`），不抛异常。
- 卡片上失败时写人话和一次动作，见 4.3 和 5.4：“制裁名单没能自动检查，点此到 OFAC 官方查一次”，链接 `https://sanctionssearch.ofac.treas.gov/`。
- 同名命中仍然必须人工排除，不得自动计分，沿用现有规则。
- 这是本版唯一“默认联网”的动作：只下载公开官方文件，不发送任何客户信息，名称匹配在本地完成。

### 4.4 P-04 分数条字符

- 分数条一律用 `■`（已填）和 `□`（未填），10 格，填充数 = round(分数 / 10)；灰色状态（需人工核实）全部用 `□`，颜色由标题里的 ⚪ 表达。

## 5. 分数卡改版（P-05 至 P-08）

分数卡是用户每次都看的唯一界面，本节给出完整的版式、取值规则和示意卡，开发 agent 按本节实现，审核 agent 按本节逐条验收。卡片只在对话里直接显示，不依赖 HTML、图片或点开文件。

### 5.0 设计原则

1. \*\*先结论后依据。\*\*第一屏（约 12 行）只回答三件事：现在能做什么、风险多大、还差什么。
2. \*\*风险和核实度分开。\*\*风险分说“发现了多少危险信号”，核实度说“查实了多少”。两者都显示，才不会把“没查到”读成“安全”。
3. \*\*每个数字都能追到规则。\*\*风险分只来自红旗权重；核实度、动作阶梯、结论句都由固定规则算出，同一证据包永远得到同一张卡。
4. \*\*不靠颜色表达。\*\*每个状态都有文字，颜色和符号只是辅助，深色和浅色界面都能读。
5. \*\*业务员能照做。\*\*没查到的项必须配“点哪里、做什么”，不写技术原因。
6. \*\*只做提示，不下定论。\*\*用“建议”“先补”这类词，不出现“骗子”“诈骗”等定性词。

### 5.1 版式总览（自上而下）

```text
[1] 标题行      ## 颜色 等级 · 风险 N/100 分数条 ｜ 核实度 M/100（高/中/低）
[2] 覆盖行      置信度：x（锚点 n/3）｜覆盖：X/8｜未覆盖：…        （沿用 v0.8.0 格式，不改）
[3] 结论行      **结论：一句话。** 客户：名称（国家/城市）· 询盘类型
  ——— 以上加 [4] 为第一屏 ———
[4] 动作阶梯    表：动作 | 建议 | 条件（4 行）
[5] 六维表      表：维度 | 状态 | 依据（6 行）
[6] 三栏        需要注意（≤3）/ 已核实（≤3）/ 没查到（≤2）
[7] 一次动作    每个“没查到”配一行：▸ 项目 — 链接：做什么
[8] 追问话术    ≤3 条，英文加一句中文含义
[9] 末行        补充建议一句 + 免责声明
```

| 规则 | 取值 |
| --- | --- |
| 整卡行数 | 不超过 45 行（含表格行），第一屏 \[1\] 到 \[4\] 不超过 14 行 |
| 标题 | 二级标题，颜色符号：🟢 低（风险 0–29）、🟡 中（30–59）、🔴 高（60–100）、⚪ 需人工核实 |
| 分数条 | 10 格，填充数 = floor(风险分 / 10 + 0.5)（四舍五入，5 进位），`■` 已填、`□` 未填；需人工核实全部 `□`。注意不要用 Python 的 `round()`，它对 85 会得到 8，Node 得到 9，两边必须一致 |
| 核实度 | 标题行只写数字和档位，不画条 |
| 分隔符 | 覆盖行沿用全角竖线 `｜`；表格用标准管道表格 |
| 禁用 | HTML 标签、颜色代码、`▓ ░ ▒`、代码块包裹整张卡 |
| 语言 | 默认中文；英文话术保留英文；客户原文、公司名保留原样 |
| 脱敏 | 人名、电话、邮箱沿用 v0.8.0 脱敏规则，卡片不出现完整号码和完整邮箱 |

### 5.2 核实度（P-05）

核实度是新增的显示指标，范围 0 到 100，**不参与风险分，也不改变等级和置信度**（边界 B19 沿用）。公式：核实度 = 对 5 个维度求 权重 × 完成度 之和，四舍五入取整。

| 维度 | 权重 | 完成度怎么算 |
| --- | --- | --- |
| 公司真实度 | 40 | 取 `layers.company.credibility`：高 1.0、中 0.6、低 0、未知 0 |
| 买家与公司的关联 | 25 | 取 `layers.person_company_link.strength`：强 1.0、中 0.6、弱 0.3、无 0、矛盾 0；若人物真实度为高且完成度小于 1，加 0.1，上限 1.0 |
| 联系方式 | 15 | 三项各 1/3：电话与自称国一致或与官网联系页一致；邮箱是企业邮箱且域名等于官网域名；域名已注册满 6 个月且官网可访问。没提供或没查的项记 0 |
| 合规口碑 | 10 | 制裁名单已查且无匹配 0.5；公开检索已做且没发现投诉 0.5；有未排除的同名命中记 0 |
| 规模匹配 | 10 | 地图规模判断为“吻合”0.5；海关或注册库记录与自称主营一致 0.5；偏小、住宅型记 0 |

- **档位**：75 及以上为高，50 到 74 为中，50 以下为低。
- **矛盾**：该维度命中积极矛盾红旗，或链接强度为“矛盾”时，该维度完成度记 0，并在六维表标“有矛盾”。具体对应：公司真实度看 RF-DOM-001/002、RF-CORP-001/002/003/004/006、RF-NEG-001、RF-SAN-001；联系方式看 RF-DOM-001/002、RF-MAIL-001、RF-CORP-005；规模匹配看 RF-CORP-002/004；买家与公司的关联看 RF-ID-002。
- **“交易行为”不进核实度**：它只显示状态（见 5.3），因为它反映的是风险而不是核实深度。
- **算例一（Harbor Rim）**：公司高 40 + 关联强 25 + 联系方式三项全对 15 + 合规两项都已查 10 + 规模没查到 0 = **90，档位高**。
- **算例二（NORDIC IMPORT AB，仿冒域名）**：公司低 0 + 关联无 0 + 联系方式全 0 + 合规两项都已查 10 + 规模 0 = **10，档位低**。

### 5.3 六维表（P-05、P-07）

| 维度 | 状态来源 | 状态词（按完成度） | 条形 |
| --- | --- | --- | --- |
| 公司真实度、买家与公司的关联、联系方式、合规口碑、规模匹配 | 5.2 的完成度 | 1.0 到 0.9：已核实；低于 0.9 到 0.6：基本核实；低于 0.6 到 0.3：部分核实；低于 0.3：未核实；矛盾：有矛盾 | 5 格，填充数 = floor(完成度 × 5 + 0.5)，同样用 `■` 和 `□` |
| 交易行为 | 命中 RF-PAY-*、RF-ACC-*、RF-BEH-\* 任一条为“有异常”；没命中且提供了询盘原文为“无异常”；没提供原文为“未核实” | 无异常、有异常、未核实 | 不画条，用 `—` |

- 状态符号：已核实和基本核实用 ✅，部分核实用 🟡，未核实用 ❓，有矛盾和有异常用 ⚠️，无异常用 ✅。
- 每行“依据”一句话，不超过 28 个汉字，只写最强的一条证据，不写技术词（见 4.3）。
- 六维表的顺序固定：公司真实度、买家与公司的关联、联系方式、交易行为、合规口碑、规模匹配。公司层放第一行，体现“公司信息权重最大”。
- 人物真实度（头像、账号时长）不单列一行，写进“买家与公司的关联”的依据里，例如“账号已使用 6 年”。

### 5.4 动作阶梯（P-06）

四级动作，每级给一个状态和一句不超过 20 个汉字的条件。状态只有三种：✅ 可以、⚠️ 有条件、⛔ 不建议。它由下表的规则算出，**只是显示，不改变风险分和等级**。输入字段：等级 L（低 / 中 / 高 / 需人工核实）、核实度档位 V（高 / 中 / 低）、公司可信度是否为低 CL、是否命中 RF-PAY-\* 或 RF-ACC-\* 的任一条 PA、阶段 S（inquiry / pre-order）、账户校验是否通过 AC、合规口碑是否已查 CP、待确认项列表 Q（`display.open_questions`，例如“品牌是否强制”“项目地点”）。

| 动作 | 规则（从上到下，第一条命中即停） | 条件文字 |
| --- | --- | --- |
| 回复和报价 | L=高 → ⚠️；其余 → ✅ | ⚠️：只做标准报价，不发定制方案 |
| 寄样和小额投入 | L=高 → ⛔；CL 或 L=需人工核实 → ⚠️；L=中 → ⚠️；L=低 且 V=低 → ⚠️；L=低 且 V=中或高 → ✅ | ⚠️：先补核实（见一次动作）；✅：条件列留空 |
| 定制和大额备货 | L=高、L=需人工核实、CL、V=低 → ⛔；L=中 → ⚠️；L=低 且 V=中 → ⚠️；L=低 且 V=高 且 CP=是 且 Q 为空 → ✅；L=低 且 V=高 其余 → ⚠️ | ⚠️：先确认 + Q 的前两项；若 CP=否：先补制裁名单检查 |
| 收定金和付款 | PA 或 L=高 → ⛔；S=pre-order 且 AC=通过 且 L 不是高 → ✅；其余 → ⛔ | ⛔：先做订单前复核（执照和收款账户）；✅：仍需电话回拨确认账户；高：不建议 |

结论句也用固定模板生成，不让模型自由发挥，按下表从上到下取第一条命中的：

| 条件 | 结论句模板 |
| --- | --- |
| L=高 | 先不要投入：不寄样、不垫付、不付款。 |
| 寄样为 ✅ 且 定制为 ✅ | 可以正常推进，收款前先做订单前复核。 |
| 寄样为 ✅ 且 定制为 ⚠️ | 可以报价、寄样；定制或大额备货前，先{定制条件}。 |
| 寄样为 ⚠️ | 可以先报价；投入前先{寄样条件}。 |
| 其他 | 信息还不足：先报标准价，不要投入。最值钱的补充：{第一项未覆盖项}。 |

判定的单元测试要把“等级 × 核实度档位 × 是否公司可信度低 × 是否命中付款类红旗 × 阶段”的全部组合都跑一遍，确认每种组合都有且只有一个结果（验收 X5）。

### 5.5 三栏风险点（P-07）

| 栏 | 放什么 | 上限 | 符号 | 排序 |
| --- | --- | --- | --- | --- |

## 6. 脚本渲染卡片（P-09）

卡片的数字、阶梯、结论句和排版由脚本 `render_card` 从证据包算出来，模型只负责检索、判断和填写一组有长度限制的文字字段。这样同一份证据包永远得到同一张卡，格式也能做快照测试。

### 6.1 分工

| 谁 | 做什么 |
| --- | --- |
| 模型（按 SKILL.md 的流程） | 检索、判断红旗、填证据包的 `checks`、`flags`、`layers`、`coverage`，并填 `display` 里的文字字段 |
| `risk_score` | 算风险分和等级（公式不变） |
| `render_card` | 算核实度、六维状态、动作阶梯、结论句；校验 `display`；排版输出 Markdown |
| 模型 | 把 `render_card` 的输出原样贴给用户，不改一个字，不自己补内容 |

### 6.2 接口

```bash
python scripts/render_card.py evidence.json            # 输出卡片 Markdown
python scripts/render_card.py evidence.json --json     # 只输出计算结果（测试用）
cat evidence.json | python scripts/render_card.py -    # 从标准输入读
```

- Python 版进精简包，Node 版 `scripts/render_card.mjs` 只在仓库里，用于一致性测试（沿用“精简包只放必要脚本”的原则）。
- 重算风险分并与证据包里的 `score` 比对，不一致就拒绝渲染，返回 `status: "score-mismatch"`（验收 E1：卡片与报告分数必须一致）。
- `display` 校验不通过返回 `status: "invalid-display"` 和错误列表，不默默修改也不渲染，让模型按错误重填。
- 输出中文和符号用 UTF-8，默认不联网，不写盘。
- 环境没有 Python 时，模型按第 5 节的规则手动排版，卡片末行加一句“（手动排版）”，测试不覆盖这种路径。

### 6.3 `display` 字段（证据包新增，可选）

旧证据包没有 `display` 也必须继续有效：缺失时 `render_card` 用确定性默认文字（维度依据用模板句，“需要注意”“已核实”从 `flags` 和 `checks` 自动生成），只是不如模型填的详细。

```json
  "dim_notes": {

    "behavior": "没要求先付款，没要求换收款账户",

    { "text": "招标信息待确认：西门子是否强制，项目在巴淡岛还是新加坡", "flag_id": null, "kind": "clue" }
  ],
  "verified": [
    { "text": "官网电话和客户一致，邮箱域名等于官网域名" }
  ],
  "missing": [
    { "text": "地图上没找到这家公司", "gain": 3,
      "action": { "label": "地图", "link_text": "在 Google 地图搜 Harbor Rim Engineering",
                  "url": "https://www.google.com/maps/search/Harbor+Rim+Engineering+Batam",
                  "instruction": "看建筑规模和门口有没有招牌，回传“吻合 / 偏小 / 住宅”" } }
  ],
  "open_questions": ["西门子是否强制", "项目地点"],
  "scripts": [
    { "en": "Could you confirm whether Siemens is mandatory or an equivalent brand is acceptable?",
      "zh": "请确认西门子是否强制，或是否接受同等品牌。" }

```

**校验规则**（全部由脚本检查）

| 字段 | 规则 |
| --- | --- |
| `customer_label`、`inquiry_type` | 必填；不超过 40 字；公司名保留原样 |
| `dim_notes.*` | 六项其中已查的必填，每项不超过 28 个汉字 |
| `attention`、`verified`、`missing` | 条数不超过 3、3、2；每条 `text` 不超过 30 个汉字；`attention[].kind` 取 `flag` 或 `clue`，`flag` 必须给 `flag_id` 且能在 `flags` 里找到 |
| `missing[].action` | 有的话 4 个字段都要填，`url` 必须是 http 或 https；不需要链接的填 `null` |
| `scripts` | 不超过 3 条；谁说话的语气和 v0.8.0 话术规则一致，不含“核实”“背调”“怀疑”“诈骗” |
| 所有文字 | 不含 4.3 表里的技术词（HTTP 状态码、MX、SPF、DMARC、RDAP、POI、CAPTCHA、API Key、“误报”），不含禁用词“骗子”“诈骗犯”；不含完整手机号和完整邮箱 |
| `open_questions` | 字符串数组，每条不超过 12 个汉字，最多 3 条 |

### 6.4 确定性要求

- 同一份证据包跑 100 次输出字节一致；不读系统时间（“域名已使用 N 年”的 N 由证据包里的检索日期和注册日期算出，不用今天的日期）。
- Python 与 Node 的输出字节一致，特别注意四舍五入用 `floor(x + 0.5)`，不要用 `round()`。
- 快照测试：把 5.7、5.8 两张示意卡和第 9 节列出的其他场景写成用例（输入证据包 + 期望卡片全文），放在现有的 `tests/cases/` 目录下，每个场景一个用例文件（精简包由构建脚本合并，不占文件数）。
- 字段缺失、值为 `null`、数组为空都要有明确的默认行为，不得抛异常；输入不是合法 JSON 返回 `status: "invalid-input"`。

## 7. 一句话入口与询盘类型（P-10、P-12）

用户只需要说一句话或贴一段询盘，Skill 自己抽出能查的信息、判断这是哪类询盘、自动跑完能跑的检查，最后只在卡片末尾请用户补“最值钱的一条信息”。这一节的内容写进 `SKILL.md` 的“工作流程”前面，作为第 0 步。

### 7.1 整体流程

1. **接收**：用户的一句话或贴文。
2. **抽取**：按 7.2 抽字段，写进证据包的 `intake`。
3. **分类**：按 7.3 选一个询盘类型，得到额外检查和话术方向。
4. **并行检索**：沿用 v0.8.0 的“免费优先与自动取证”和三层核实，制裁名单自动下载（见 4.2）。
5. **形成证据包**，由 `risk_score` 算风险分，由 `render_card` 渲染卡片。
6. **输出**：直接在对话里显示卡片；用户说“出完整报告”再写文件。

### 7.2 抽取字段（`intake`）

| 字段 | 怎么抽 | 缺失时 |
| --- | --- | --- |
| `company` | 大写开头的机构名，带 Ltd、LLC、GmbH、Pte、Group、Co.、公司等后缀优先 | 标 `null`，靠邮箱域名或网站反查 |
| `person` | “I am X”、签名、聊天昵称 | `null` |
| `email`、`domain` | 邮箱正则；文中的网址；企业邮箱的域名不一定是官网，沿用“官网画像优先”规则 | `null` |
| `phone` | 带 `+` 或 `00` 的号码交给 `phone_check`；不带的不猜国家 | `null` |
| `country`、`city` | 文中自称、区号、官网地址；冲突时不合并，分别记录 | `null` |
| `product`、`quantity`、`amount` | 询盘中的型号、数量、金额 | `null` |
| `inquiry_text` | 原文保留在内存，证据包只存摘录和脱敏后的引用句 | 空 |
| `inquiry_type` | 按 7.3 | `general` |
| `best_next` | 信息增益最大的一条补充（如“补一个企业邮箱”） | 自动取第一项未覆盖项 |

抽取仍由模型完成（不新增脚本，精简包的文件预算见第 9 节），但最终写进证据包的字段和枚举值要符合本表。脱敏沿用原规则，证据包里不出现完整手机号和完整邮箱。

**不追问规则**：只要公司名、域名、邮箱、电话、社媒主页任一项存在就直接开始，不先问问题。一项都没有才问一次：“请补一项：公司名、邮箱、电话或网站”。

### 7.3 询盘类型

类型只用来选额外检查和话术方向，**不改风险分和红旗权重**，也不新增红旗。一次只选一个，选不准就用 `general`。

| 类型（枚举值） | 识别线索 | 额外检查 | 话术方向 |
| --- | --- | --- | --- |
| `tender` 招标邀请 | tender、bid、RFQ、ITT、截标日期、标书 | 按 7.4 的 T1 到 T4 | 确认指定品牌、项目地点、截标日、付款条件 |
| `sample` 索要样品 | sample、free sample、用对方快递账号、运费到付 | 收货地址是否货代或住宅；是否要求先付样品费（已有 RF-PAY-001） | 样品费和运费的常规安排，要企业收货地址 |
| `large_first_order` 大额首单 | 首次询盘就给出大金额、不议价直接下单 | 强调“规模匹配”维度（地图、海关、注册库），提示订单前复核 | 确认采购周期和分批交货安排 |
| `account_change` 换收款账户 | 通知银行账户变更、要求付给第三方 | 阶段设为 `pre-order`，走订单前复核和 `account_check` | 用留档电话回拨确认（RF-ACC-001 话术） |
| `pre_order` 订单确认 | PO、合同、要求给收款账户 | 同上，并检查执照和税号 | 索要执照和账户开户信息 |
| `general` 一般询盘 | 其他 | 默认检查 | 要公司资料和部门 |

### 7.4 招标专项（P-12，P2）

截图里的客户就是一个招标邀请，招标类询盘常见的套路是收标书费、保证金、验厂费。这 4 项只作线索，结果写进“需要注意”“已核实”或“没查到”，**不新增红旗**。

| 编号 | 检查 | 怕什么 | 怎么查 |
| --- | --- | --- | --- |
| T1 | 招标真实性 | 项目根本不存在 | 用招标编号、项目名和采购方名在公开搜索里查公告；查不到只记“没查到” |
| T2 | 费用 | 收标书费、保证金、验厂费 | 询盘原文里是否要求投标前付费；命中按已有 RF-PAY-001 计分 |
| T3 | 采购方职能 | 对方根本不在采购岗 | 领英现任职位是否含 procurement、purchasing、项目采购，与自称职位匹配（需登录时走一次动作） |
| T4 | 规格和品牌合理性 | 规格后面是假型号 | 指定品牌和型号能否在品牌官网查到；查不到只记线索 |

### 7.5 检索深度

默认“标准”：跑全部免费通道和三层核实。用户说“快查”就只跑本地脚本和一次公开检索（域名、邮箱、电话、制裁、公司名一次搜索），不查地图、海关、社媒，核实度自然偏低，卡片顶部加一句“快查模式：未查地图、海关、社媒”。开始前用一句话告诉用户“正在查：官网、制裁名单、地图…”，不要刷屏。快查和标准都不改变评分规则。

### 8.1 注册库自动查（P-11）

目前注册库只在 `country_capabilities.json` 里给链接，没有自动查。本版在 `scripts/identity_check.py` 里新增子命令 `registry`（不新增文件），对有免费公开接口的国家自动查公司求存在和状态，其余国家维持链接。

```bash
python scripts/identity_check.py registry --country GB --name "EXAMPLE TRADING LTD" --online
```

| 规则 | 内容 |
| --- | --- |
| 默认离线 | 不加 `--online` 只返回注册库链接；联网时只发送公司名和国家，不发送人名、邮箱、电话 |
| 每次请求 | 最多 2 次、串行、带间隔、超时 10 秒，失败返回 `status: "unavailable"` 和原因 |
| 匹配 | 公司名规范化后完全一致且国家一致才算找到；多条同名返回 `ambiguous`，不合并，卡片写“有多家同名公司，需要确认” |
| 返回字段 | 只返回公司层信息：`legal_name`、`status_text`、`incorporation_date`、`address_country`、`source_url`、`retrieved_at`；**不返回、不显示、不保存董事和股东个人信息**（B14 数据最小化） |
| 作用 | 找到且状态正常，算公司层的“独立佐证”（可把公司可信度提到高）；注册地址所在国与官网所在国、电话区号或自称国对不上，属于 RF-CORP-001 已有定义（含“注册地址”），按原规则计分；状态是注销、解散或成立日期晚于自称，本版不计分，写进“需要注意”（kind 填 clue）并提示人工复核，是否为它新增红旗见第 13 节 Q6；没找到只降置信度 |
| 测试 | CI 里不联网，用虚构公司的固定响应文件（放在现有 `tests/fixtures/` 里） |

**哪些国家先做（候选，全部需开发 agent 逐一核对后才能实现）**

| 候选 | 要核对的点 |

| 英国 Companies House | 是否需要免费 API Key？谁来申请？没有 Key 时是否直接回退到链接 |
| 挪威 Brønnøysund、法国企业目录等欧洲公开数据 | 是否无 Key、限流、商用许可 |
| 新加坡 ACRA 公开数据集 | 是否有公司级实时查询，还是只有批量文件；若只有批量文件就不做 |
| 对中东和东南亚试点国家（沙特、阿联酋、马来西亚、印尼、越南等） | 多数没有免费公司级接口，维持链接加一次动作，不要硬实现 |

验收的一个重点：即使只实现 1 个国家也算完成，关键是 `registry` 的接口、匹配规则、隐私限制和测试都符合上表，并且可以按这个模式扩展到更多国家。
