# BuyerCheck 迭代规划 v0.8.0（第四版）

Oct 30, 2026 · @Daniel

## 1. 概述

v0.8.0 把核实的重心从“单条红旗”改成三层：**先查公司，再查买家和这家公司有没有强链接，最后才看买家个人的社媒账号像不像真人**。公司信息（官网、主营、能力）占主导地位，人物账号只是辅助。

这来自负责人 2026-10-30 的两点要求：

- 重点观察买家和背调出的公司有没有强链接，社媒里的蛛丝马迹能体现关联，例如领英工作经历里有当前公司、公司官方 Facebook 里出现该员工的照片和名字。
- 判断“真实存在的人、非机器人”：头像先自动比对并给出判断加链接，业务员肉眼判断只做最终决定；再看社媒账号的使用时长和分享、照片的丰富程度。

| 编号 | 内容 | 类型 | 优先级 |
| --- | --- | --- | --- |
| C | 公司层强化：官网画像、主营一致性对比、官网与官方社媒互相指向 | 核实模型 | 高 |
| L | 人-公司链接分级（强 / 中 / 弱 / 矛盾） | 核实模型 | 高 |
| P | 人物真实度：头像图像比对、账号时长与厚度 | 辅助判断 | 中 |
| T | `identity_check` 脚本（官网画像提取、图像比对） | 脚本 | 中 |
| R | 新红旗 RF-CORP-006（主营不一致，权重 2，负责人已确认） | 规则 | 中 |

**这一版不做**：自动人脸识别或人脸相似度匹配；用户名跨平台枚举；批量抓取社媒；列出公司其他员工。详见第 9 节。评分公式、等级色带、覆盖率分母（仍为 8）都不变。

## 2. 现状基线（v0.7.0，2026-10-30 实测）

仓库已到 v0.7.0：跟踪 81 个文件，历史已改写（全部提交里搜不到真实客户的姓名、邮箱），所有测试通过，比赛精简包 27 个文件（上限 28）。下面只列和本版相关的现有能力和缺口，其他不重做。

**已有（不要重做，在此基础上扩展）**

| 能力 | 位置 | 当前做法 |
| --- | --- | --- |
| 官网画像 | `data-sources/global.md` 第八节、报告 1.3 | 从邮箱后缀找官网，抓主页、About、Products、Contact，比对联系页姓名和电话 |
| 社媒双匹配 | `global.md` 第六节 | 名称加电话（或域名）同时匹配才算，只同名记 `name-only-match` |
| 地图、海关 | `global.md` 第六节 | 地图按电话和公司名双向查；海关多平台、免费优先 |
| 头像反搜 | `collection_checklists.md`、RF-ID-001 | 业务员用 Google Lens、TinEye 反搜后回传，命中另一个身份才计分 |
| 任职比对 | RF-ID-002 | LinkedIn 显示的公司或职位与自称不一致才计分 |
| 新号无活动 | RF-ID-003 | 账号创建不足 30 天且无实质内容才计分 |
| 公司页与官网互指 | `collection_checklists.md` 第 3 节 | LinkedIn 公司页和官网是否互相指向，业务员回传两个链接 |
| 调查链接清单 | 报告附录 C | 列出本次访问过的全部链接，含未命中和需登录的 |

**缺口（v0.8.0 要补的）**

1. 没有把“买家和公司的关联”作为独立、分级的结论。现在的身份锚点里，企业邮箱只证明“这个邮箱属于这个域名”，没证明“这个人在这家公司”。
2. 公司层的检查散在各个清单里，没有统一的“公司可信度”分档。
3. 官网页脚的社媒链接没有自动提取，“官方账号”靠按名字搜。
4. 头像只靠业务员反搜回传，没有自动的同图比对。
5. 账号时长和内容厚度只有 RF-ID-003 一条。
6. 官网、官方社媒、海关之间的主营一致性没有规则。

## 3. 三层核实模型

三层按顺序做：上一层确认了，下一层才有意义。公司层最重，买家的个人账号最轻。

&#91;embedded content: 三层核实模型 · 3 层，依次决定\]

左边是三层各自回答的问题，右边是它对置信度的作用。蓝色加粗的公司层权重最大。

**置信度规则（只升不降，不改现有行为）**

| 编号 | 规则 |
| --- | --- |
| R1 | 基础置信度沿用 v0.7.0：锚点 ≥2 为高，1 个为中，0 个为低。A1–A14、评测集、一致性测试不改就必须通过 |
| R2 | 链接层为「强」且公司层不是「低」：置信度至少为「高」，即使锚点只有 1 个 |
| R3 | 公司层为「低」（含至少一项积极矛盾，如主营不一致、地址住宅却自称工厂）：置信度封顶「中」，卡片标「公司层存疑」 |
| R4 | 人物真实度为「高」：置信度至少为「中」，但单独不能抬到「高」 |
| R5 | 三层只改变置信度和卡片显示，风险分只由红旗权重决定，公式不变 |

若 R3 导致现有测试结果变化，说明现有用例里有积极矛盾却标成了「高」，agent 必须停下来问负责人，不要改测试。

## 4. 公司层：先把公司查透

公司层输出一个**公司可信度**（高 / 中 / 低 / 未知），由固定规则从检查结果推出，同一输入结果相同。所有检查都遵守现有纪律：查不到只降置信度，只有积极矛盾才计分。

**检查项**

| 检查项 | 看什么 | 正向信号 | 积极矛盾（计分红旗） |
| --- | --- | --- | --- |
| 官网真实性 | 域名年龄、能否访问、联系信息是否齐全、内容是否原创、公司名与域名是否一致 | 域名 ≥6 个月、地址电话邮箱齐全、产品页有深度 | RF-DOM-001 仿冒域名、RF-DOM-002 域名过新、RF-CORP-001 信息矛盾 |
| 主营与能力 | 产品线、认证、工厂或产能、展会、案例客户、成立年份 | 具体、可验证，与询盘品类相符 | 见下方 RF-CORP-006 |
| 地图 | 地址是否存在、类型、商家电话、招牌 | 地址类型与自称规模相称、电话一致 | RF-CORP-002、RF-CORP-003 |
| 海关 | 进出口品类、角色、频次 | 品类、角色与询盘吻合 | RF-CORP-004 |
| 官方社媒 | 官网页脚或联系页链接指向的页面、简介是否回链官网、主营是否相关、页面创建时间和活跃度 | 官网与社媒页“互相指向”、内容与主营相关、页面存在时间长 | RF-ID-003 类条件（新建且无内容）、RF-CORP-006 |
| LinkedIn 公司页 | 与官网是否互指、行业、员工规模与官网自称是否相近 | 互指、行业一致、规模相近 | RF-CORP-006 |
| 负面与制裁 | 现有 RF-NEG-001、RF-SAN-001 | — | 已有 |

**“官方”账号怎么认定**：只把官网页脚或联系页里的社媒链接所指的页面当作官方候选；该页面的简介或网站字段再指回官网域名，才算“互指”（强）。只是按公司名搜到的主页记“名称匹配”（弱），和现有的 `name-only-match` 一致。

**地图规模合理性（名称、地址、电话都对得上之后，还要做）**

名称、地址、电话都对得上，只证明“有这个地方”，不证明“是这个规模”。负责人 2026-10-30 要求：还要判断工厂和公司的体量是否合理，体量很小或地址像家庭地址，都要留意。

| 看什么 | 怎么看 | 小体量或可疑的信号 |
| --- | --- | --- |
| 建筑类型与体量 | 街景和卫星图里的层数、占地、外观 | 自称工厂，却只是一间民房、小店面或写字楼里的单间 |
| 周边环境 | 工业区、商务区还是纯居民区 | 自称工厂，却在居民小区内 |
| 招牌与门牌 | 门口是否有公司名 | 没有招牌、没有公司名 |
| 同址公司 | 是否多家公司共用同一地址 | 共享办公、虚拟地址 |
| 商家页信息 | 照片、评价数量、营业时间 | 无照片无评价（只降置信度，不计分） |
| 自称规模的来源 | 官网写的厂房面积、员工数、产能；询盘的采购量 | 自称与所见差距悬殊 |

**判断规则**

- 只有“自称规模大”和“所见体量小或住宅型”同时成立，才算积极矛盾，并入 `RF-CORP-002`（权重 2 不变）。判定细则要扩写：命中条件增加“体量明显偏小”。
- 贸易公司、小型进口商的办公室小很正常。官网和询盘自称就是小公司或贸易商时，体量小不算矛盾，只在卡片写“体量小，注意订单金额”，不计分。
- 住宅型地址（在家办公）在很多国家合法，单独出现不计分；叠加“自称工厂、大公司或大订单”才计分。
- 街景可能是旧图，结论卡要写明街景日期。
- 输出：地图规模判断 = 吻合 / 偏小 / 住宅型 / 无法判断，附地图和街景链接。有浏览器工具且已登录就一步到位查看，没有就“链接加清单”，由业务员回传所见。
- 小体量加大订单时，建议提高订单前复核的要求（见 v0.6.0 订单前复核流程）。

**主营一致性对比（“对比采样”）**：把官网、官方 Facebook、LinkedIn 公司页、海关记录各自显示的主营，用不超过 3 个关键词概括，填进一张对比表，每格标“一致 / 部分一致 / 明确不同 / 未查”。询盘品类只作参照列，不单独触发红旗。

**RF-CORP-006 主营不一致（权重 2，负责人已确认）**

- 命中：至少两个独立来源（官网、官方社媒、LinkedIn 公司页、公司级海关记录）显示的主营行业大类明确不同。
- 不命中：只有一个来源；查不到；官网自称综合贸易商（多品类视为一致）；只是与询盘品类不同。
- 证据：并列各来源的主营摘要和链接。

**公司可信度分档（确定性规则）**

| 档位 | 条件 |
| --- | --- |
| 低 | 命中 RF-DOM-001、RF-DOM-002、RF-CORP-001、RF-CORP-002、RF-CORP-003、RF-CORP-004、RF-CORP-006、RF-NEG-001、RF-SAN-001 中任一条 |
| 高 | 不是低，且官网已验证、主营与能力已记录、至少有 1 个独立佐证（地图、海关、官方社媒互指、LinkedIn 公司页互指之一） |
| 中 | 不是低，官网已验证，但没有独立佐证 |
| 未知 | 没有官网也没有任何公司痕迹（不计分，只在卡片上标“公司层未查到”） |

说明：同名不同公司（名称、电话、网站任一不同）不得合并，沿用 v0.7.0 规则。

## 5. 人-公司链接层：买家是不是这家公司的人

公司层确认后，这一层回答：这个买家和这家公司有没有强链接。输出**链接强度**：强 / 中 / 弱 / 无 / 矛盾。强度取所有证据里最高的一档，出现积极矛盾时直接定为“矛盾”，不再升级。

| 强度 | 证据 | 条件 |
| --- | --- | --- |
| 强 S1 | 官网团队页或联系页列出此人的姓名（和职位） | 且与买家提供的邮箱或电话对得上 |
| 强 S2 | 官方 Facebook 页的帖子或照片里出现此人的姓名和照片 | 页面必须是与官网“互指”认定的官方页；姓名和照片同时对得上，只有姓名算“中” |
| 强 S3 | LinkedIn 个人页现任公司就是这家公司，且该公司 LinkedIn 页（与官网互指）的员工列表里有此人 | 需登录状态，未登录跳过 |
| 强 S4 | 企业邮箱域名等于官网域名，且经官方公布的总机或公共邮箱确认过此人 | 不用客户自己给的电话（沿用原防伪原则） |
| 中 M1 | LinkedIn 个人页现任公司是这家公司 | 但公司页员工列表里看不到此人或看不到列表 |
| 中 M2 | 企业邮箱域名等于官网域名 | 但官网上没有此人 |
| 中 M3 | 展会名录、行业协会、新闻、公司级海关联系人等第三方把此人和这家公司放在一起 | 来源独立于买家自己提供的信息 |
| 弱 | 只有买家自称；或只是同名搜索不能区分是否同一人 | 不算链接 |
| 无 | 查过了但什么都没找到 | 只降置信度，不计分 |
| 矛盾 | LinkedIn 显示的现任公司或职位与自称不一致 | 已有 RF-ID-002（权重 3），不新增红旗 |

官网上没有此人（M2）不算矛盾，团队页本来就不会列出所有人，查不到只降置信度。

**员工照片和姓名的核对规则**

- 只查买家这一个人。不枚举、不记录公司其他员工的姓名和照片。
- 姓名比对用精确匹配加常见变体（中文名拼音、英文名缩写）。
- 照片比对只用第 6 节的图像比对（同图或近似图）加业务员肉眼判断，不做自动人脸识别。
- 任职起止时间、帖子日期要与买家自称的任职时间吻合。
- 不下载、不保存员工照片，证据只记链接和比对结果（同图 / 不同 / 无法比对）。
- 遇到登录墙就跳过，写「未核实（未登录）」，不扣风险分；有浏览器工具且已登录就一步到位，否则“链接加清单”，由业务员回传。

**证据包里的记录格式**：`person_company_link.evidence[]` 每条包含类型（S1–S4、M1–M3）、来源链接、检索时间、取得方式（auto / browser / user-reported）。

## 6. 人物真实度层：这个账号像不像真人

这一层只回答“这是真实存在的人还是机器人、假号”，输出**人物真实度**（高 / 中 / 低 / 未知）。它在三层里最轻，只显示、不扣风险分，单独最多把置信度抬到“中”（见第 3 节 R4）。

### 6.1 头像：自动图像比对 + 业务员最终判断

1. **收集**：从已打开的页面、浏览器工具或业务员提供的图片地址拿到各平台头像（Facebook、Instagram、LinkedIn、WhatsApp）。没有登录、取不到图的就跳过。
2. **自动比对**：用感知哈希判断是不是同一张图或裁剪、缩放后的近似图。
3. **反搜链接**：生成 Google Lens、TinEye 链接，由浏览器或业务员打开看有没有命中另一个身份。
4. **给出判断 + 链接**：列出自动结果、各平台头像链接、反搜链接。
5. **业务员肉眼判断只做最终决定**：“是同一个人 / 不是 / 不确定”，记入证据包 `human_verdict`。

| 自动结果 | 含义 | 对人物真实度 |
| --- | --- | --- |
| 同图复用 | 至少 2 个平台用同一张图 | 弱正向，需反搜没有命中他人 |
| 近似图 | 同一张图的裁剪或缩放 | 同上 |
| 不同图 | 各平台图不同 | 中性，交给业务员肉眼判断，不扣分 |
| 无法比对 | 取不到图、登录墙、尺寸太小 | 中性 |
| 反搜命中另一身份 | 照片属于别人 | `RF-ID-001`（权重 3，已有），人物真实度为低 |

**限制**：不做人脸识别、人脸相似度匹配或提取人脸特征；图像只在内存里比对，不保存；“不同图”不扣分，因为真人常常在不同平台用不同照片或 logo。AI 生成的人脸在网上反搜不到，所以“反搜没命中”不等于“真人”，这也是头像只能当辅助、不能单独拍板的原因。

### 6.2 账号使用时长与内容厚度

真实人的社媒账号通常存在很久、有多方位的分享和照片；骗子即使做戏，账号也多半是新建的。

- **时长**：负责人 2026-10-30 确认，页面创建时间、管理员所在国家、账号加入时间这几项都要用，**但只用公开可见的**。三条规则：(1) 公开可见就记入证据（取得方式、链接、截图日期）；(2) 登录后才看得到、或页面没有显示的，写“未公开”，不猜、不计分，也不要求业务员为此去找管理员；(3) 都看不到时回退到“活动跨度”：最早一条带日期的内容到最近一条，主页创建日期、最早工作经历年份、最早推荐信日期作补充。各平台这些字段现在是否真的公开，以业务员实际看到的为准，agent 实现时不要写死“某平台一定显示”。
- **厚度**看这几项：多个年份的内容、不同场景和不同人物的照片、别人的评论和标记、共同联系人、内容原创而非全是转发、语言与所在地一致、互动的账号看起来是真人。

| 档位 | 条件 | 计分 |
| --- | --- | --- |
| 厚实 | 活动跨度 ≥2 年，且厚度信号 ≥3 项 | 不计分，正向 |
| 一般 | 介于两者之间 | 不计分 |
| 单薄 | 账号创建不足 30 天且无实质内容 | 命中 `RF-ID-003`（权重 2，已有，条件不变） |

**两点要写进规则**：真人新号也有（新入行、换号），所以“新”本身不扣分，只有“新且空”才计分；老号也可能被买卖或盗用，老号但最近才改名、改公司、改头像，或内容的语言和地区突然变了，要记为“账号近期被改动”线索（不计分），这种情况不升人物真实度。

### 6.3 人物真实度分档（确定性规则）

| 档位 | 条件 |
| --- | --- |
| 低 | 命中 `RF-ID-001` 或 `RF-ID-003` |
| 高 | 不是低，且账号厚实，且（多平台同图或近似图，或业务员终判为同一人），且没有“账号近期被改动”线索 |
| 中 | 不是低，账号厚实或一般，但不满足高的全部条件 |
| 未知 | 没找到买家的社媒，或未登录跳过（不扣分） |

## 8. 实现：脚本、文件预算、测试

新增一个脚本 `scripts/identity_check.py` / `.mjs`，用子命令区分功能，这样精简包只多 1 个文件（27 → 28，刚好到上限）。

| 子命令 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| `site` | 提取官网画像：公司名候选、简介、社媒链接、联系邮箱和电话、地址、团队页和联系页链接、版权年份 | 官网域名（联网时）或 `--html-file`（离线用例） | JSON，查失败返回 `status: "unavailable"` |
| `backlink` | 检查一段社媒页简介文字或 HTML 里是否指回官网域名 | 官网域名 + 社媒页文本或 `--html-file` | `mutual: true / false / null` |
| `image` | 两张或多张头像的同图、近似图比对 | 本地图片路径 | `same-image / near-duplicate / different / not-comparable` |

**设计要点**

- `site` 默认不联网，只在用户显式加 `--online` 时才请求；联网时只访问公司官网（不访问个人社媒），每次最多 4 页、串行、带间隔、遵守 robots.txt 的保守精神。
- `backlink` 只处理调用方给它的文本或 HTML，不自己去抓 Facebook、LinkedIn 页面（登录墙、条款限制）。页面内容由浏览器工具或业务员回传。
- `image`：没装图像库时只能判断“文件完全一致”（用 SHA-256），其他情况返回 `not-comparable`，原因 `no-image-library`。装了可选库（Python 的 Pillow、Node 的 sharp，许可证未核实，实现前必须核对）才用 dHash，按汉明距离分档。阈值先用建议值，用合成测试图标定后写进代码注释，不要凭感觉定。
- 图像只在内存里比对，不写盘、不保存哈希、不输出图像内容；不调用任何人脸检测或识别库。
- 查询失败、取不到图都不抛异常，输出与现有脚本一致的 JSON。

## 9. 边界与硬性约束

v0.7.0 的 B1–B12 全部继续有效（见 `docs/iteration_plan_v0.7.md` 第 3 节），下面是本版新增或收紧的部分。遇到冲突时停下来问负责人。

| # | 规则 | 理由 |
| --- | --- | --- |
| B13 | **不做自动人脸识别、人脸相似度匹配、人脸特征提取**。头像只做“同图或近似图”的图像比对，“像不像同一个人”由业务员肉眼终判 | 人脸比对可能进入生物识别范围（[GDPR 前言第 51 条](https://gdpr-info.eu/recitals/no-51/)：照片只有经“特定技术手段”处理才算生物识别数据，其他地区法规我没核实），且对低分辨率头像和 AI 生成人脸不可靠 |
| B14 | **数据最小化**：只查买家这一个人，不枚举公司其他员工；图像不写盘、不保存哈希；证据包只记链接和比对结果 | 个人信息保护，也和 B1 一致 |
| B15 | 不自动抓取 Facebook、Instagram、LinkedIn 页面；这些页面只通过已登录的浏览器工具查看，或由业务员回传 | 平台条款限制自动采集；LinkedIn 曾就抓取行为起诉（仅见搜索结果标题，未核对） |
| B16 | 头像“不同图”、账号“新”、排查不到都不单独扣分；只有 RF-ID-001（反搜命中他人）、RF-ID-003（新且空）等已有积极矛盾才计分 | 一贯的“查不到只降置信度”纪律（D7） |
| B17 | 公司层最重：三层之间的优先关系只写在第 3 节 R1–R5 里，不得在脚本里另定规则 | 保持可复现、可测试 |
| B18 | 不复制任何第三方项目代码；可选依赖（Pillow、sharp）只能作为可选，核对许可证后再写入 `data-sources/global.md` | 沿用 B5、B9、B10 |
| B19 | 不改评分公式、等级色带、覆盖率分母；现有全部测试不改就必须通过 | 向后兼容 |
